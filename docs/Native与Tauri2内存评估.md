# My Snip 原生与 Tauri 2 技术选型评估

评估日期：2026 年 10 月 18 日。目标平台为 Windows 和 macOS，目标功能是截图识别公式、检查与编辑、选择输出格式、复制后自动收起。

选型结果：用户已选择 C，即 Tauri 2 按需创建并销毁 WebView，优先完成可用版本。本文保留选型时的估算和依据；当前开发方案见[系统设计](SYSTEM-DESIGN.md)。

## 结论与可供选择的范围

如果优先控制使用中的内存，选择无 WebView 的原生界面更合适；代价是两端界面及公式排版需要更多适配。如果更希望共用一套界面，Tauri 2 可采用按需创建、复制后销毁 WebView 的策略，降低长时间待机的开销，但打开窗口时仍需预留百 MiB 级内存。

以下是针对 My Snip 的工程预算估计，全部尚未经过本项目原型测量。区间是为了选型预留的量级，不是官方指标、公开基准的统计区间，也不是验收上限。按完整应用相关进程及必要辅助进程考虑，单位为 MiB；1 MiB = 1048576 字节。

| 路线 | 托盘待机 | 打开单个公式结果窗 | 单屏 4K 截图和识别的短时峰值 |
| --- | ---: | ---: | ---: |
| A 无 WebView 的原生界面 | 约 10–40 | 约 40–120 | 约 100–250 |
| B Tauri 2 窗口隐藏但保留 WebView | 约 80–220 | 约 100–300 | 约 180–450 |
| C Tauri 2 按需创建并销毁 WebView | 目标约 20–60，待辅助进程回收后验证 | 约 100–300 | 约 180–450 |

这些区间覆盖 Windows 与 macOS 的选型预算，不意味着两平台有相同结果。显卡驱动、系统版本、屏幕分辨率、字体缓存、公式排版实现和辅助进程回收都会改变测量值；5K、6K 和跨屏截图可超出上表的峰值预算。原生路线的预算以轻量公式排版实现成功为前提，不包含完整 TeX 工具链。

对你提出的“轻量、低内存”要求，真正需要选择的是 A 或 C。B 仅作为保留窗口以换取快速再次显示的比较项。

## 比较的功能和实现前提

所有路线都应提供同一组功能：全局快捷键、单屏框选、在线多模态接口、截图与公式预览、编辑 LaTeX、四种输出格式、默认偏好、系统明暗、密钥保存、复制后返回原应用。在线模型运行在服务端，本地不加载模型权重。

| 项目 | A 原生界面 | C Tauri 2 按需创建界面 |
| --- | --- | --- |
| Windows 窗口 | Win32 原生控件和绘制，Rust 或 C++ 对接 | Tauri 2 与系统 WebView2 |
| macOS 窗口 | Swift 配合 AppKit | Tauri 2 与系统 WKWebView |
| 共享逻辑 | Rust 负责接口、会话、格式和图片处理 | Rust 负责接口、会话、格式和图片处理 |
| 界面代码 | 两套平台界面，保持同一交互规范 | 共用一套小型 HTML 与 TypeScript 界面 |
| 公式预览 | 原生绘制或无浏览器的 SVG 排版链路，需验证 | 可直接使用本地打包的 KaTeX |
| 收起后的处理 | 释放截图、公式资源和临时窗口 | 保存必要状态到 Rust，销毁所有用完的 WebView |
| 主要成本 | 两端 UI、文本输入、排版与构建维护 | WebView 运行时开销、冷创建延迟与平台差异 |

这里的原生特指不在结果窗内嵌浏览器引擎。若原生界面为了预览公式又嵌入 WebView2 或 WKWebView，活动内存就会向 Tauri 路线靠拢，不能继续使用 A 的预算。

Tauri 官方说明其核心进程负责本机能力，界面运行在系统 WebView 中；Windows 使用 WebView2，macOS 使用 WKWebView。复用系统引擎能减少随应用分发的内容，但引擎运行时仍会分配内存。[Tauri 进程模型](https://v2.tauri.app/concept/process-model/)

## 内存估计的依据与证据限度

### Tauri 的依据

微软明确说明 WebView2 使用多进程架构，浏览器、渲染和 GPU 等相关进程会带来内存与启动开销，实际占用受页面内容及实例数量影响。因此不能把 Rust 主进程单独显示的十几 MiB 当作整个 Tauri 应用的开销。[WebView2 性能说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)

Hopp 作者公开的一个 MacBook Pro 单次实验，在同时打开六个窗口后报告 Tauri 约 172 MB。该实验发表于 2025 年 4 月，作者明确标注样本量为一次。它支持将打开 WebView 后的资源预算放在百 MB 量级，但不是 My Snip、不是 Windows 结果，也不能用 172 除以六预测单窗占用。[Hopp 原始实验](https://www.gethopp.app/blog/tauri-vs-electron)

当前没有同一份 My Snip 原型在两平台的可比测量，所以本报告不提供“必然节省多少百分比”的结论。

### 原生的依据

原生路线可以避免创建完整 WebView 进程组。托盘、快捷键和轻量配置逻辑可由编译后的本机程序维持，打开结果窗时才分配图片、文本布局和公式资源。上表的 10–40 MiB 待机与 40–120 MiB 活动区间是按这种实现约束制定的预算，当前没有证明它们能在 My Snip 中达到。

原生方案仍要控制字体、图像、图形资源和排版引擎；仅把前端语言换成 Swift、Rust 或 C++，不能保证整个应用处于某个固定内存值。Windows 应分别观察工作集与私有提交；Apple 平台的 memory footprint 又有自己的计量口径。两平台分别验收，不把不同指标的数值直接混在一起比较。[Windows 内存分析](https://learn.microsoft.com/en-us/windows/apps/develop/performance/disk-memory)、[Apple 内存计量说明](https://developer.apple.com/videos/play/wwdc2022/10106/)

## 原生路线的主要风险是公式排版

已有视觉稿包含实时的公式预览，不能在比较原生时只计算一个文本输入框的开销。原生路线需要保留对分式、矩阵、多行表达式、上下标和编辑后重排的支持。

可验证的方向是先在无浏览器环境将公式转换成 SVG，再交给本机图形层显示。MathJax 官方提供使用轻量 DOM 适配器进行服务端转换和 SVG 输出的示例；QuickJS 是可嵌入的 JavaScript 引擎。因此可以调查“裁剪并预打包的 MathJax + QuickJS + 原生 SVG 显示”这条路径。[MathJax 直接调用与 SVG 输出](https://docs.mathjax.org/en/v4.1/server/direct.html)、[QuickJS 官方介绍](https://bellard.org/quickjs/)

这条组合是待验证的工程设计：MathJax 的 Node 示例不能直接证明它能在 QuickJS 中运行。模块加载、字体数据、异步加载和 SVG 兼容都需要最小原型验证，不能暗中引入 Node 或 WebView 后仍按低开销原生方案计算。如果这一验证失败，应重新估算 A 的活动内存、兼容范围和开发工作量。

原生方案的首个验证应覆盖 20 个代表性公式，包括矩阵、多行公式、积分、希腊字母、中文说明和较长表达式，检查排版、修改后刷新、资源释放和内存峰值。无需先完成两套界面再发现排版实现不合适。

## 截图本身造成的短时开销

以下为像素大小计算，不是框架测试。以每像素四字节的 RGBA 图像为例：

| 画面 | 一份原始图像 | 两份原始图像副本 |
| --- | ---: | ---: |
| 3840 × 2160 | 31.64 MiB | 63.28 MiB |
| 5120 × 2880 | 56.25 MiB | 112.50 MiB |
| 6016 × 3384 | 77.66 MiB | 155.32 MiB |

截图冻结、遮罩背景、GPU 纹理、PNG 编码和跨进程复制可能让多份数据短暂共存。PNG 文件很小也不代表解码后的位图很小。两条路线都应在裁切完成后立即释放整屏图像，只把小裁片交给识别请求和结果预览。

Tauri 路线尤其应避免把整屏 PNG 反复编码成 Base64，通过 JSON 发给多个 WebView。框选期间只针对当前显示器处理，配置页复用结果窗口，不同时保留多个设置或预览窗口。具体遮罩是否采用本机绘制，会影响实现成本和峰值，需要一起验证。

## Tauri 的收起策略决定长期占用

隐藏窗口只改变可见性，界面、JavaScript 堆、DOM 和浏览器辅助进程可能继续存在。若复制后只调用隐藏操作，就更接近表中的 B 路线。

C 路线建议让 Rust 常驻负责托盘、快捷键与设置，按需创建结果 WebView。复制成功后先收起以满足交互要求，再销毁该次界面并释放图片；状态只保留必要的非敏感偏好。下次截图重新创建结果窗。Tauri 提供销毁窗口及关闭 WebView 的接口，但这些接口不保证系统的辅助进程和缓存立即归零。[Tauri 窗口生命周期](https://v2.tauri.app/reference/javascript/api/namespacewebviewwindow/#destroy)

Windows 还提供 WebView2 的低内存目标和挂起机制，不过微软将其描述为尽力而为的优化，可能涉及缓存清理或换出。它们不能替代“关闭后整个应用相关内存是否下降”的测量。[WebView2 内存管理](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance#use-memory-management-apis)

销毁 WebView 的代价是再次打开时需要重新初始化。对截图次数较少、长期托盘待机的工具，这个取舍值得考虑；如果连续截图频率很高，可设置一个短暂复用期，但需接受复用期内较高的内存占用。

## Windows 和 macOS 的交付成本

两条路线都需要在真实 Windows 和 Mac 上测试截屏权限、多屏与 Retina 或 DPI 缩放、系统主题、输入法、托盘或菜单栏、剪贴板及焦点恢复。选择 Tauri 只能共享更多界面代码，不能免去这些本机验收。

| 比较项 | A 原生界面 | C Tauri 2 按需创建 |
| --- | --- | --- |
| 内存优化上限 | 更适合严格控制活动时占用 | 需要承担打开 WebView 的固定成本 |
| 两端界面开发 | 高，分别对接系统 UI | 较低，共用一套界面 |
| 公式排版开发 | 高，需要先证明无 WebView 路线可用 | 较低，可沿用 KaTeX |
| 再次唤起 | 窗口和资源更容易按需管理 | 销毁策略下要重新创建 WebView |
| 后续界面功能增加 | 通常涉及两端修改 | 通常可共用前端修改 |
| 长期低占用 | 更有优势，但仍需实测 | 可通过生命周期管理争取较低待机占用 |

工作量无法在公式引擎和双端截图验证前可靠换算成天数。当前可以判断 A 的主要额外投入是两套界面与排版适配；C 的主要额外投入是 WebView 生命周期、两种浏览器引擎差异和资源回收。

## 选择规则与下一步

如果你的要求接近“待机尽量低于 30 MiB，打开窗口也尽量低于 100 MiB”，优先验证 A。它最符合严格低内存目标，但 100 MiB 应作为努力目标，不应在原型之前当作保证。

如果你能接受使用时约 100–300 MiB，主要希望长期待机不维持这个占用，并希望两端共用一套界面，优先验证 C。不能仅凭更小的安装包就认定它满足内存要求。

选定方向后，先做同功能最小原型，再修订系统设计和正式开发。验证应使用 release 构建，关闭开发服务器、调试器和 DevTools，统计本应用对应的全部辅助进程；不能将整台机器的所有 WebView2 进程计入本应用，也不能漏算本应用使用的进程。

建议至少测量冷启动待机、结果窗打开、4K 截图、编辑公式、复制关闭后 30 秒与 120 秒，以及连续 50 次截图。记录稳定值、峰值、回落情况和再次唤起耗时。Windows 同时记录私有工作集与私有提交，Mac 记录可归属的 memory footprint，并补充相关图形内存。两平台结果分开列出。

本报告完成的是资料核对、位图容量计算和工程估算，尚未测量功能原型。选型已确定为 C，后续以内存回落和使用体验的实际测量检验该决定。
